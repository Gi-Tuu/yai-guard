## 1. P0-1 · Controller Docker 执行环境（已修复）

**根因**：`deploy/compose.sandbox.yaml` 用 `backend/Dockerfile` 构建 controller，而该镜像**不含 Docker CLI**；controller 以 uid 10001 运行，也没有处理 docker.sock 的组权限。服务能启动，但一执行就失败。

**修复**
- 新增 `backend/Dockerfile.controller`：多阶段从 `docker:27-cli` 只拷 `docker` 二进制；Python 服务 + 非 root uid 10001。
- `compose.sandbox.yaml`：
  - 构建改用 `Dockerfile.controller`；
  - `group_add: ["${DOCKER_GID}"]` 只加 socket 所在组；
  - `read_only` + `cap_drop: ALL` + `no-new-privileges`；
  - `SANDBOX_RUNTIME` 默认 `runc`；
  - `healthcheck` 调 `/healthz`。
- `controller.py`：启动时 `ensure_ready()` 检查 **daemon / runtime / 镜像**；失败 `/healthz` 503，`create` 显式报错。
- `.env.example`：新增 `DOCKER_GID` 与取值方法。

**证据**：[`docs/evidence/P0-1-controller-docker.md`](evidence/P0-1-controller-docker.md)
- controller 镜像 322 MB；容器内 `uid=10001`，socket `root:root 660`（Docker Desktop gid=0）；
- healthz 返回 daemon 29.7.2 / runtime runc / image ok；
- create → python `42` → 只读根拒绝 → 无网络 → 文件读写 → destroy，残留 0；
- **app 镜像 `NO_DOCKER_CLI`**，app compose 不挂 socket。

**信任边界**：docker.sock ≈ 宿主 root。controller 非 root 只缩小应用层被直接拿下的面；socket 仍是高权限通道。生产 `DOCKER_GID` 必须按宿主机 socket 实际 GID 配置。

## 3. P1-1 · 审批严格布尔（已修复）

**原问题**：`bool(body.get("approved", False))` 会把 `"false"` 当成 `True`。

**修复**：`approved` 缺失或 `type(...) is not bool` → **422**；校验任务存在、属于当前 principal、call_id 属于该任务、未重复审批（409）；审批结果由 Agent loop 写入 `approval.resolved`。

测试（`test_api.py`）：JSON `true/false` 通过；`"false"`、`"true"`、`1`、`0`、`null`、缺字段全部 422；重复 409；错误 owner 404；未知 call 404。

## 4. P1-2 · 统一 API 鉴权（已修复）

- 新增 `_require_principal` 依赖：`X-Demo-Token`（可配 `DEMO_TOKENS` 多 token），token → 短 hash principal；任务记录 `owner`。
- 所有任务接口（创建/状态/SSE/trace 下载/trace 校验/审批）统一鉴权；`/healthz` 与 `/api/policy` 明确公开；静态资源公开。
- 跨 owner 访问返回 **404**（不泄露任务是否存在）。
- `APP_ENV=production` 且未配置 token → **import 阶段直接失败**；开发/测试匿名必须显式 `ALLOW_ANONYMOUS=1`。
- SSE 改为 `fetch + ReadableStream` 带 header（EventSource 不能带自定义 header），trace 下载改为带 header 的 fetch blob。

测试：无 token 创建/读任务/SSE/trace 全 401；错误 token 401；token B 访问 token A 任务 404；正确 token 200；生产空凭证启动失败由 import 检查覆盖。

## 5. P1-3 · 输出内存限额（已修复）

**原问题**：`subprocess.run(capture_output=True)` 先把全部输出读进宿主机内存，再截断。

**修复**：`run_bounded()` 双线程持续 drain，每路只保留 8 KB；总输出超 1 MB 立即 kill 进程组；超时同样 kill；超时/超限对容器 `docker kill`。返回 `truncated` / `killed_reason`。

证据（[`P1-3-bounded-output.md`](evidence/P1-3-bounded-output.md)）：10 MB stdout → 宿主持有 8,207 字节，`truncated=true`、`killed_reason=output_limit`、exit -9；5 项单测覆盖大 stdout/stderr、双通道死锁、超时。

## 6. P1-4 · Trace 完整性增强（已修复）

新增 `verify_trace_file()`，区分：

| 维度 | 检查 |
|---|---|
| Hash-chain integrity | 逐条重算 sha256(prev + canonical(event)) |
| Sequence continuity | seq 必须 1..N 连续 |
| Log completeness | completed 任务必须含 `task.completed` 且末事件 `sandbox.destroyed`；failed 任务必须含 `task.failed` |
| Anchor | 独立 `.anchor.json` 记录事件数与 final hash；末尾删除/追加可检出 |
| Authenticity（可选） | `TRACE_HMAC_KEY` 存在时校验 anchor HMAC |

API `/trace/verify` 返回 `ok / chain_ok / sequence_ok / completeness_ok / anchor_ok / authentic / bad_seq / events / final_hash`。

测试（7 项新增）：正常通过、空文件、删末条、缺终止事件、seq 跳跃、anchor 不匹配、HMAC 篡改。

**诚实边界**：SHA-256 链只证明“生成后未被改”，不能证明“记录完整”；anchor/HMAC 只有在密钥不被攻击者掌握时才有意义。README 不宣称“不可篡改”。

## 9. 关键安全决策

1. **不做自动 runtime 降级**：降级会让“安全档位”变成不可信承诺；显式失败比静默降级诚实。
2. **Controller 非 root + socket 组**：满足最小必要权限；但明确 socket = 宿主 root 的信任边界。
3. **统一鉴权 + owner**：token 只存 hash；跨 owner 一律 404；生产空凭证拒绝启动。
4. **SSE 不走 query token**：改用 fetch header，避免 token 进入 URL/代理日志。
5. **审批严格布尔**：不做任何隐式转换；重复审批 409。
6. **输出双重限额**：单路 8 KB + 总 1 MB；超限 kill 进程组并杀掉容器。
7. **Trace 分层结论**：链、序号、完整性、锚点、HMAC 分开返回，不混淆“防篡改”与“不可篡改”。

## 12. 剩余风险

1. docker.sock 访问 = 宿主 root 等价；controller 被完全控制时仍可控制宿主 Docker。缓解：独立 VM、非 root、只挂 socket、app 不挂。
2. 策略仍可被静态绕过（编码/两段式/符号链接等）；容器边界是兜底，已写入文档。
3. Trace 锚点/HMAC 密钥与日志同机；拥有宿主权限的攻击者可同时改两者。当前定位是“防意外/低成本篡改”，不是防有权限攻击者。
4. 单进程内存限流/并发；多 worker 失效。
5. 沙箱镜像使用 tag（`python:3.12-slim`）未固定 digest。
6. Docker Desktop 本地 socket gid=0；Vultr 上必须按实际 `DOCKER_GID` 配置。
7. gVisor 未实测；Vultr 双 VM、公网 HTTPS、真实推理 **BLOCKED**（无资源/未授权）。
