## 1. 结论（TL;DR）

| 项 | 结论 |
|---|---|
| **主方案** | **Docker hardened + `runc`（已本地实测）；gVisor `runsc` 仅预留、未实测、不自动降级**。参数：默认网络 `none`、`--cap-drop=ALL`、`--read-only`+`tmpfs`、`--pids-limit`、`--memory/--cpus`、非 root `--user`、无 `docker.sock`、无宿主目录挂载、默认 seccomp + AppArmor、cgroup v2。 |
| **为什么不把 microVM 当主方案** | 5 天窗口内，microVM 路线（Microsandbox / Firecracker）**全部依赖宿主 `/dev/kvm`**：Microsandbox 官方 Linux 文档明确「local sandboxes use hardware virtualization…KVM is available through `/dev/kvm`」。KVM 是否在所选 Vultr 机型/区域可用，只能在 Day-0 实测，**不能在 11-03 之前假定**。把它当主方案 = 把整个 demo 押在一个未验证的内核能力上。 |
| **为什么不裸用 gVisor 作为唯一方案** | gVisor 的默认平台 `systrap` 不需要 KVM（官方文档：`systrap` 自 2023 年中起成为默认，`ptrace` 已不推荐），因此它在普通 Vultr Cloud Compute 上就能跑 —— 但它是**同宿主用户态内核**，仍复用宿主内核做部分系统调用路径；用它做「加分项」比做「唯一防线」更合理，且必须有一条 30 秒内可切回的降级路径。 |
| **备选（Plan B，Day-1 若 KVM 可用则启用）** | **Microsandbox on Vultr VX1**（Vultr 官方 sandboxing 指南的方案：microVM + libkrun + KVM，独立内核、CPU/内存限额、默认阻断同宿兄弟沙箱互访）。 |
| **降级路径（若 gVisor 在 Vultr 上跑不起来）** | ①`runsc` 不可用 → 回落默认 `runc` + 更严 seccomp/AppArmor/网络/资源限额（控制面一个环境变量 `SANDBOX_RUNTIME` 即可切换，见 §5.4）；②`runsc` 可用但业务镜像 syscall 不兼容 → 只对「不可信代码执行」任务切 `runsc`，依赖安装阶段用 `runc`；③若演示需要「独立内核」叙事且 KVM 可用 → 切 Microsandbox（≥1.5 人日）。 |

**一句话安全故事**：*Agent 的执行永远发生在与应用进程不同的 PID/ mount/ network / cgroup 边界之外；默认零网络、零 capability、只读根文件系统、PID 与内存硬限额；所有动作写链式审计；危险动作在策略层先被拦，再被内核层兜住。*

### 2.2 Vultr 官方 agent sandboxing 指南（这一页决定了「官方参考架构」）

来源：<https://docs.vultr.com/how-to-set-up-agent-sandboxing-on-vultr-cloud-compute>（访问 2026-10-31）。

| 事实 | 原文摘录 |
|---|---|
| 官方指南选择的是 **Microsandbox**，不是 Docker | “Agent sandboxing runs code an AI agent generates inside an isolated environment… **Microsandbox** is an open-source platform built for this, launching each sandbox as its own microVM on `libkrun` over the Kernel-based Virtual Machine (KVM), with a separate kernel from the host rather than the shared-kernel isolation a container provides.” |
| 机型要求 | “Have access to a **Vultr VX1™ Cloud Compute** instance running **Ubuntu 24.04** as a non-root user with sudo privileges.” |
| KVM 前置 | `sudo usermod -aG kvm $USER`；`newgrp kvm`；`id`；`ls -l /dev/kvm`（“Verify the output reports a character device that belongs to the `kvm` group.”） |
| 安装 | `curl -fsSL https://install.microsandbox.dev | sh`（安装 `msb` + `libkrunfw` 到 `~/.microsandbox`） |
| Host 自检 | `msb doctor` 输出含 `✓ CPU virt svm`、`✓ KVM device /dev/kvm`、`✓ KVM access read/write` |
| 资源限额 | `msb create --name sandbox01 --cpus 1 --memory 256M debian`；`msb status` 显示 `1 / 1`、`256 MiB / 256 MiB` |
| **默认网络** | “Verify the sandbox has outbound internet access by default.”（`REACHABLE`）——**默认放通公网**，这对我们要额外加策略 |
| 沙箱互访 | “Microsandbox denies traffic between separate microVMs by default… Each sandbox reaches the public internet, but not its siblings.” |
| 文件进出 | `msb copy /tmp/hostfile.txt SANDBOX_NAME:/tmp/hostfile.txt`、`msb copy SANDBOX:/tmp/result.txt ...` |
| MCP 接入 Agent | `npx -y microsandbox-mcp`，通过 `opencode.json` 注册 |

> 结论：**Vultr 官方参考架构 = VX1 + KVM + microVM**；官方同时把「Docker strongly recommended」写进赛题必需栈。二者不冲突：赛题允许「containers **or** throwaway instances」，官方指南是 microVM 的一条具体落地路径。

## 4. 候选方案对比矩阵

评分符号：**◎ 强 ／ ○ 可用 ／ △ 勉强 ／ ✕ 不满足**。

|---|---|---|---|---|---|---|---|
| **隔离强度（共享内核 vs 独立内核）** | △ 共享宿主内核，namespace+cgroup+cap+seccomp | ○ 共享宿主内核，但**系统调用经用户态内核（Sentry）**，攻击面大幅缩小 | ◎ 独立内核 microVM（硬件虚拟化） | ○ 取决于后端 secure runtime（gVisor/Kata/Firecracker），默认 runc = △ | ◎ microVM（但不在你的 Vultr 上） | ◎ 独立内核 microVM | ◎ 独立 VM（最强边界） |
| **启动延迟** | ◎ 约百毫秒级（估算，未实测） | ◎ 官方未给数字；第三方表格标 gVisor +10–50ms（**第三方，未核实**） | ○ 秒级创建（官方未给数字，**估算**） | △ Docker 模式同容器；K8s 模式更重 | ○ 秒级（云端） | ○ microVM 启动快，但需自制 rootfs/网络 | ✕ 15s 级 provision + 引导脚本（**主路径不可接受**，可异步预热池缓解） |
| **CPU/mem/pids/磁盘限制** | ◎ `--cpus`、`--memory`、`--memory-swap`、`--pids-limit`、`--ulimit`、`--storage-opt size`（overlay2+xfs pquota 条件） | ◎ 同左（与 runc 共用 Docker 资源参数） | ○ `--cpus`、`--memory`（`msb create --cpus 1 --memory 256M`），pids 级限额**未核实** | ○ API `resourceLimits` 支持 CPU/内存/GPU | ○ 按 vCPU/RAM 售卖，pids 不可控 | △ 自己设 vCPU/mem/rate limiter，pids 需 guest 内配 | ◎ 整机额度 |
| **网络 egress 控制粒度** | ○ `--network=none` 最硬；细粒度需 bridge+iptables/代理 | ○ 同左；注意 gVisor 对部分 netfilter 能力有限（第三方称 gVisor 不实现 iptables `nat` 表，**未核实**） | ◎ 内置策略：默认阻断 private/host/loopback/link-local/metadata，支持 `--no-net`、`--net-default-egress deny`、域名规则（strict 模式 fail-closed）、TLS 拦截 | ◎ egress sidecar + DNS/nftables 策略 + Credential Vault（较完整） | △ 无固定出网 CIDR，需自建代理 | ✕ 需自己搭网络栈（tap/CNI/iptables） | ○ 靠 Vultr 防火墙组（VPC/Firewall Group），粒度到端口/CIDR，域名级需代理 |
| **文件进出** | ◎ `docker cp` / bind mount / 输出摘要 | ◎ 同左 | ◎ `msb copy SANDBOX:/path` | ◎ SDK `files.write_files` / `read_file` | ◎ SDK files API | △ 需自制（vsock/FS） | ○ `scp`/API，但每次要传 |
| **5 天可落地性（含演示）** | **◎ 最高**：Docker 官方强烈推荐，零内核特性依赖 | **○ 较高**：`apt install runsc` + `runsc install` + `--runtime=runsc`，1 个参数切换 | △ 中：KVM 未验证 + 安装脚本 + 安全策略需补齐（默认放通公网） | △ 低：多一层控制面 + execd + SDK 适配 | ✕ 不满足赛题（不在 Vultr） | ✕ 低：自建 VMM 编排 | △ 中低：API 编排 + 镜像引导 + 回收，容易在 demo 现场翻车 |
| **运维复杂度** | ◎ 单机 Docker，日志/指标现成 | ○ 多一个 runtime 二进制与升级路径 | ○ 单二进制 + doctor，但 KVM/glibc 前置 | ✕ 控制面 + 数据面 + 存储（SQLite/PG）+ 可选 k8s | ○ 托管（但不可控） | ✕ 高 | ✕ 需要实例池/回收/配额 |
| **成本** | ◎ 0 额外（同机） | ◎ 0 额外 | ○ VX1 强依赖（4c16g $0.12/hr） | ◎ 0 额外 | △ 按秒计费外部支出 | ○ 需裸金属/大机型 | △ 实例费 + 闲置 |
| **满足「沙箱与应用进程隔离」** | ◎（不同容器/命名空间，`--network=none`、无 `docker.sock`、无宿主挂载） | ◎（更强） | ◎ | ○（同机容器，需另配 secure runtime） | ✕（不在 Vultr 上） | ◎ | ◎ |
| **额外收益** | 与 CI/本地一致，调试最快 | **可讲「用户态内核」安全叙事**，同时保 Docker 生态 | 可讲「独立内核 + microVM」最强叙事 | 可讲「标准化 sandbox 协议」 | — | — | 可讲「一次性基础设施」 |
| **额外风险** | 共享内核（内核 CVE 即逃逸面） | 业务镜像 syscall 兼容性（matplotlib/numpy 一般 OK，`iptables`/`mount` 类不行） | **KVM 不可用 = 全线阻塞**；默认 egress 放通需加固 | 组件多、5 天集成成本 | 违规 | 工程量大 | 冷启动/回收/费用 |

**矩阵结论**：在「5 天 + 必须能演示 + 不能赌未验证内核特性」的约束下，**唯一没有单点阻塞的方案是 Docker**；gVisor 是「在同一套 Docker 参数上额外加一层用户态内核」的低成本增强，具备 30 秒回切能力。

### 4.1 矩阵读法：三个决定性维度

不要平均看十个维度，实际只有三条会改变结论：

| 决定性维度 | 为什么它决定生死 | 本次取值 |
|---|---|---|
| **① 依赖未验证的内核特性吗？** | 11-03 才开始，任何「要 KVM / 要 nested virt / 要特定机型区域」的方案都是**不可恢复的阻塞**（换机型意味着换区域、重建、重测） | Docker/gVisor：不依赖（`systrap`）。Microsandbox/Firecracker：依赖 KVM → 只能当 B 计划 |
| **③ 出问题时能不能 30 秒回退？** | demo 只有一次机会 | `SANDBOX_RUNTIME=runc` 一个环境变量切换；Microsandbox 需要换机型 + 重装 = 小时级 |

> 换句话说：矩阵的十个维度里，**只有「隔离强度」是加分项，另两条是「能不能交」的地板线**。Docker hardened 满足地板线且隔离强度可接受（`--network=none` + 只读根 + 无 cap + 默认 seccomp 的组合，对「rm -rf / fork bomb 外联」三类演示威胁是充分的）；gVisor 把「隔离强度」从 △ 提到 ○，成本是 1 条 `--runtime` 参数 + 1 个 apt 包。

## 5. ADR-001 决策

### 5.1 决策

**采用 Docker hardened + `runc` 作为当前唯一已验证运行时；gVisor `runsc` 仅作为未来可选档，未在本轮实测，控制器不会自动降级。**

- 沙箱边界实现形式：**每任务一个一次性容器**（`--rm`，任务结束 `docker rm -f`），容器名带 `task_id`，镜像只读。
- 应用进程（FastAPI 控制面）**不进入**沙箱：双 VM 落位下，控制面 VM **没有 Docker**，只通过 VPC 私网调用 sandbox VM 上的 Sandbox Controller（共享 token）；Controller 在**本机**经 unix socket 调 Docker，以 `docker exec`/`docker cp` 操作容器。任何情况下都不把 `docker.sock` 挂进沙箱。
- 网络：默认 `--network=none`；仅「依赖安装阶段」切入 `yaig-egress` 专用 bridge + 正向代理白名单（见 04 §8）。
- 资源：`--cpus=1`、`--memory=512m --memory-swap=512m`、`--pids-limit=128`、`--ulimit nofile=512:512`、wall-clock `timeout`（Docker `--stop-timeout` + 应用层 `timeout` 双保险）。

### 5.2 为什么不是 Microsandbox 做主方案

1. **单点依赖 KVM**：官方明说 Linux 本地运行依赖 `/dev/kvm`；而 `/dev/kvm` 是否出现在我们实际拿到的 Vultr 机型/区域，**今天无法核实**（普通 Cloud Compute 未核实；VX1 有官方指南背书但需要换机型 + 可能在 NY 区域，见 VX1 文档「Currently available in New Jersey (`ewr`)」）。
2. **默认网络是放通的**：官方指南演示的就是「默认能访问公网」。我们要的安全故事要求「默认零网络 + 白名单」，等于要在 Microsandbox 上再做一遍策略层（`--no-net`/`--net-default-egress deny` 可行，但要新增配置面与验证）。
3. **5 天里它是「第二套系统」**：microVM 路线意味着新的 CLI/SDK、新的文件进出方式（`msb copy`）、新的指标与日志（`msb metrics/logs`）、新的故障模式（KVM 权限、glibc、reflink）。

> 因此：**Microsandbox = Plan B（Day-1 若 KVM 验证通过且主方案遇到容器逃逸叙事不足时启用）**，而不是 11-03 的默认路径。


| 方案 | 淘汰理由 |
|---|---|
| 裸 Firecracker | 需 KVM（官方 tested platforms 全为 `*.metal`）+ 自建 kernel/rootfs/jailer/编排，5 天不可行。 |
| 每任务一次性 Vultr 实例 | 边界最强，但 provision ≥15s + 引导镜像 + 回收编排，demo 现场风险高；保留为「P3 加分项」（赛后/时间富余时用 Vultr API 做一条异步演示分支）。 |

### 5.4 降级路径（必须写进代码，不是写在文档里）

```
runtime_pick():
  1) runsc_probe(): docker run --rm --runtime=runsc alpine true   # Day-0 与每次启动各测一次
     ├─ 成功 → SANDBOX_RUNTIME=runsc（默认档）
     └─ 失败 → SANDBOX_RUNTIME=runc（硬化档），并在 UI/审计里标注 "runtime_fallback=runc"
  2) 若某任务 runsc 执行失败（syscall 不支持 / 退出码异常 159/160）：
     → 单任务重试一次 runc，同时在审计 trace 记 degraded=true
  3) 若需「独立内核」叙事且 /dev/kvm 可用（Day-1 决策点）：
     → 切 Microsandbox（预算 1.5 人日：安装 + 策略 + 文件进出 + 演示 1 个 containment moment）
  4) 若 demo 前 4 小时 runsc 出现不稳定：
     → 关闭 runsc（一个环境变量），只用 hardening 参数 + 04 文档的隔离话术
```

### 5.6 我们与 Vultr 官方参考架构的差异（为什么没照抄官方指南）

| 维度 | Vultr 官方 sandboxing 指南 | YAI Guard ADR-001 | 差异是否有风险 |
|---|---|---|---|
| 隔离机制 | microVM（libkrun + KVM） | 容器（runc/runsc） | 有：共享内核 vs 独立内核。用「零网络 + 只读根 + 无 cap + 默认 seccomp + gVisor」把差距压低；并用 L2 策略层与审批门补「行为级」控制 |
| 机型 | VX1（`ewr`） | 任意 Cloud Compute / VX1 均可 | 无：不绑机型 = 不绑区域 = 不阻塞 |
| 依赖 | `/dev/kvm` + `kvm` 组 + glibc ≥2.28 | 仅 Docker + Linux 5.6+（gVisor 档） | 无：依赖面显著更小 |
| 默认网络 | 公网可达（官方演示即 `REACHABLE`） | `--network=none`，仅安装阶段白名单 | 我们的默认更严，但安装阶段需要自建代理（工作量 +0.5 人日） |
| 文件进出 | `msb copy` | `docker cp` / tmpfs 卷 | 无 |
| 与赛题关系 | 官方**推荐**路径之一 | 赛题允许「containers **or** throwaway instances」，且注明 Docker strongly recommended | 无：合规 |

> 结论：官方指南回答的是「怎么在 Vultr 上搭一个 microVM 沙箱」；赛题问的是「怎么做一个 containment-first 的产品」。前者是**一种**实现，后者是**必须满足的约束集合**。在 5 天窗口内，能满足约束集合且不引入未验证依赖的方案只有一个。
