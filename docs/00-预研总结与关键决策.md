- 选型：主 `deepseek-v4.1-flash-1017`（1M ctx，$0.15/$0.60 per 1M，tools ✓）；快速便宜 `qwen3.8-flash-next`（$0.10/$0.20）；vision `qwen3.8-27b`（$0.15/$1.00，MVP 用不到）。
- 限流：chat 默认 **120 请求/分钟、16 并发**；单请求约 9 分钟；默认输出 32,768 token；429 带 `Retry-After`；并发超额会排队最多 2 分钟。
- 两个必须写进代码的坑：**模型 ID 写错不报错、静默回落 `deepseek-v4.1-flash-1017`**（启动时白名单校验 + 响应 `model` 回显写审计）；**末条 assistant 消息会被当 prefill 续写**（Agent 循环禁止）。
- 成本：一次 20 轮任务约 12.9 万 input + 3.4K output ≈ **$0.021**（目录价）/ **$0.08**（保守平铺价）。
- 详见 [`02-Vultr-Serverless-Inference接入.md`](02-Vultr-Serverless-Inference接入.md)。

### ⑤ 沙箱方案选择 —— 已决策（ADR-001）

七方案 × 12 维对比后，只有一条不受未验证内核特性阻塞的路径：

| 方案 | 结论 | 理由 |
|---|---|---|
| **Docker hardened（runc）** | **基线，必做** | 赛事 Docker strongly recommended；零内核特性依赖；`--network=none` + `--read-only` + `--cap-drop=ALL` + cgroup 限额可覆盖 `rm -rf`/fork bomb/外联三类演示威胁 |
| **Docker + gVisor（runsc/systrap）** | **默认强化档（Day-0 通过才启用）** | 系统调用经用户态内核，攻击面显著缩小；**systrap 不需要 `/dev/kvm`**；一个 `--runtime` 参数 + 一个 apt 包；失败 30 秒回切 |
| Microsandbox on VX1 | Plan B | 独立内核最强，但强依赖 `/dev/kvm`（普通 Cloud Compute 未核实），且默认放通公网需再收紧；5 天内是"第二套系统" |
| OpenSandbox | 淘汰（留作设计参考） | 能力对口但引入控制面 + execd + SDK 三层，5 天性价比低 |
| E2B | 淘汰 | 沙箱在 E2B 云上，**不满足 "on Vultr"** |
| 裸 Firecracker | 淘汰 | 需 KVM + 自建 kernel/rootfs/jailer/编排 |
| 每任务一次性 Vultr 实例 | P3 加分项 | 边界最强但 15s+ 冷启动与回收编排，demo 风险高 |

- 关键判断：**不把 demo 押在未验证的内核能力上**；"隔离强度"是加分项，"能不能交"是地板线。
- 详见 [`03-沙箱方案选型.md`](03-沙箱方案选型.md)。

### ⑥ 宿主机与沙箱的安全边界 —— 已设计到可执行参数

- **不变量 I1–I7**：永不共享 PID/mount/network/IPC、无 docker.sock、无宿主挂载、默认无网、每次执行有硬限额、沙箱零凭证、任务结束必销毁、全链路哈希链审计。
- **分层 L0–L5**：L0 宿主/控制面（持密钥、只 append 审计）→ L1 容器运行时（cap-drop/只读根/cgroup/seccomp/AppArmor）→ L2 沙箱内（只写 `/workspace`、命令规则）→ L3 网络（默认 `--network=none`，安装阶段才走白名单代理）→ L4 凭证（沙箱内为零）→ L5 审批（R0/R1/R2/R3 分级）。
- **可直接执行的加固 `docker run`**（cap-drop、no-new-privileges、read-only + tmpfs、pids/mem/cpu、uid 65534、ipc=none、AppArmor docker-default）。
- **20 条危险命令规则（D-01…D-20）+ 白名单（A-01…A-03）+ 审批门**；并明确"命令过滤不是安全保证，容器边界才是"——这句话要主动讲给评审。
- **3 个 containment moment 脚本 + 宿主未受影响取证**：M1 `rm -rf --no-preserve-root /` → `Read-only file system`；M2 fork bomb/死循环 → `fork: retry: Resource temporarily unavailable` + pids 卡在 128；M3 `curl | sh` + 云元数据 → 策略拒绝 + `Could not resolve host`，容器内只有 `lo`。
- 详见 [`04-安全边界与策略设计.md`](04-安全边界与策略设计.md)。

### ⑦ MVP 架构 —— 已定稿

- 组件：Web → Caddy → FastAPI → Agent Runtime（单循环）→ Policy Engine → **Sandbox Controller（仅它持有运行时权限）** → 一次性容器；Trace Store 全程记录；Model Adapter 唯一 provider = Vultr。
- 信任模型：用户输入、LLM 输出、沙箱输出**全部不可信**；策略引擎是确定性代码，不调用 LLM。
- **双 VM 落位**：`yai-app`（Web/API/Agent/Policy/Trace/密钥）与 `yai-sandbox`（Sandbox Controller + Docker，零密钥）经 VPC 私网通信。
- 详见 [`05-MVP架构设计.md`](05-MVP架构设计.md)。

## 4. 范围边界：做什么 / 不做什么

**做（P0）**：Web 任务入口 · 单 Agent 规划执行 · Vultr 推理（tool calling）· 一次性沙箱容器 · 终端执行 + 超时 · 文件读/写/diff · 策略拦截 + 规则可解释 · cgroup 资源限额 · 审计 trace + JSONL 导出 · 双 VM 部署 + HTTPS · 视频/README/slides。

**不做（P2，写进 README 管理预期）**：浏览器自动化（Pattern B）· 多 Agent 协作 · 用户体系/多租户 · 长期驻留会话 · 每任务一次性 Vultr 实例 · K8s/OpenSandbox · MCP 插件市场 · 移动端。

**与 YAI Agent Core 的边界**：
- 允许复用（接口层）：Agent Runtime loop 形状、任务规划数据结构、工具注册机制、MCP 客户端、模型适配接口。
- 必须独立实现：Sandbox Runtime、Execution Policy、Terminal Executor、File Isolation、Security Controller、Resource Limits、Execution Trace。
- **独立新仓库**，不 vendor 主仓库；**唯一的未核实项**：YAI Agent Core 的许可证是否与 MIT 兼容。若不兼容，只借鉴设计、不复制代码，并在 README 声明（11-02 前确认）。
- 硬红线：任何代码路径都不得在宿主机执行用户/模型产生的命令。落地手段：双 VM 架构 + 静态检查（`api/`、`agent/`、`policy/` 禁止出现 `subprocess`/`os.system`/`eval`/`exec`）。

## 6. 失败模式与预案（写死，避免临场慌）

| 场景 | 预案 |
|---|---|
| gVisor 不可用 / 不兼容 | 切 `runc` 硬化档（1 个环境变量），安全叙事改为"双 VM 网络边界 + 硬化容器 + 零凭证"；不阻塞交付 |
| KVM 不可用 | 放弃 microVM，保留 Docker；README 写"实测该机型无 `/dev/kvm`"（诚实反而加分） |
| 双 VM 网络不通 | 11-03 当晚上线可先用单 VM（同机容器），11-05 前再拆；拆机 <30 分钟 |
| 推理 tool calling 异常 | 退化为"受控 JSON 输出 + 服务端 schema 校验"；接口层已隔离，改动局限在 Model Adapter |
| 模型静默回落 | 启动白名单校验 + 响应 `model` 回显写审计；发现即 fail-fast |
| credits 不够/未到账 | 先自费 <$20 跑通 MVP；$200 到账后再扩；成本上限已被证明很低 |
| 视频录不出来 | 降级为"屏幕录制 + 旁白"，不求剪辑；主线彩排时必须一遍过 |
| 提交表单异常 | 11-08 白天先交一版可用材料，之后允许覆盖；不要等到最后一小时 |
